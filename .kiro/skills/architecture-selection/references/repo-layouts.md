# Repo Layouts, Naming and Ownership

Read this file in Phase 5 of architecture-selection to fill in `.kiro/steering/structure.md`. Copy only the section for the chosen option. Rename folders to match what the team actually uses, and delete folders the project does not need. Do not create these folders yourself; the walking-skeleton spec (quick-spec) does that.

## Common to every option

```text
.kiro/
  steering/            product.md, tech.md, structure.md (always-on), optional fileMatch files
  specs/<feature-name>/  requirements.md, design.md, tasks.md (written by quick-spec)
  skills/              team skills (this one included)
docs/
  decisions/           NNNN-<slug>.md ADRs (written by architecture-selection)
  BUGS.md              bug log (written by bug-fix, created on first entry)
README.md              what it is, how to run it, demo link, architecture diagram
.gitignore             .env*, node_modules/, __pycache__/, build output, IaC output
                       (.aws-sam/, cdk.out/), amplify_outputs* if generated
```

## Option A: serverless with AWS SAM + React (Vite)

```text
frontend/
  src/
    api/               typed client for backend endpoints (one place for the base URL)
    components/
    pages/
  package.json
backend/
  template.yaml        SAM: every AWS resource (API, functions, table, bucket, auth)
  samconfig.toml       deploy settings per environment
  src/
    handlers/          one module per route group, e.g. items, uploads, ai
    lib/               shared code: db access, bedrock client, validation, responses
  tests/
  requirements.txt     or package.json for a Node.js backend
```

Sandbox per teammate: deploy with a stack name suffix, e.g. `sam deploy --stack-name <project>-<member>`, and pass the stage as a template parameter so resource names do not collide.

## Option A with AWS CDK (TypeScript infra)

```text
infra/
  bin/app.ts           app entry; reads a stage name (member or "demo") from context
  lib/app-stack.ts     or split stacks: data-stack.ts, api-stack.ts
  cdk.json
backend/src/handlers/  as in option A
backend/src/lib/
frontend/              as in option A
```

## Option A-lite: minimal serverless

```text
frontend/              static site (plain HTML or Vite)
backend/
  template.yaml        one function with a function URL, plus one table or bucket
  src/handler.py       or handler.mjs
```

## Option B: Amplify Gen 2 full-stack

```text
amplify/
  backend.ts               defineBackend({...}); extra AWS resources via CDK here
  auth/resource.ts         defineAuth
  data/resource.ts         defineData: models and authorization rules
  storage/resource.ts      defineStorage
  functions/<name>/
    resource.ts            defineFunction
    handler.ts
src/                       frontend (or app/ for Next.js App Router)
amplify_outputs.json       generated by sandbox/deploy; never hand-edit
package.json
```

Sandbox per teammate: `npx ampx sandbox` (it is named after the local OS user; add `--identifier <handle>` if two teammates could collide in the shared account). The shared demo deploys from a connected Git branch in the Amplify console.

## Option C: container

```text
app/
  Dockerfile
  src/
  tests/
frontend/                  only if the app does not serve the UI itself
infra/                     CDK: VPC (no NAT unless required), ECS cluster, Fargate service,
                           load balancer, ECR repository, table or database
docker-compose.yml         local development only
```

## Naming conventions (all options)

- **Folders and files:** follow the language norm (kebab-case for TS/JS files and folders, snake_case for Python modules).
- **Environment variables:** UPPER_SNAKE, e.g. `TABLE_NAME`, `BUCKET_NAME`, `MODEL_ID`, `ALLOWED_ORIGIN`.
- **AWS resource names:** `<project>-<stage>-<thing>`, lowercase. The stage is a teammate's handle for a personal sandbox, or `demo` for the shared stack. S3 bucket names are global across all AWS accounts, so let the IaC tool generate them instead of hard-coding one.
- **IaC logical IDs:** PascalCase, e.g. `ItemsTable`, `ApiFunction`.
- **Branches:** `main` is always demo-ready. Use `feature/<short-name>` for features (quick-spec uses `feature/<feature-name>-fe`, `-be` and `-infra` per stream) and `fix/bug-<n>-<short-name>` for bug fixes, with small pull requests that are merged often.
- **Commits:** Conventional Commits (`feat(<scope>): ...`, `fix(<scope>): ...`, `docs: ...`, `chore: ...`); bug-fix adds a Symptom/Root cause/Fix/Test body.
- **Tags:** every resource carries `project=<name>`. Set it as a default tag in the IaC tool.

## Ownership for 3 people (default; adjust to Phase 1 skills)

| Area | Owner | Reviewer | Covers |
|---|---|---|---|
| Frontend and demo UX | Member 1 | Member 2 | `frontend/` (or `src/` in option B), screenshots, demo recording |
| API and data | Member 2 | Member 3 | handlers, shared libs and contracts, data model, backend tests |
| Infra, AI and delivery | Member 3 | Member 1 | IaC (`template.yaml`, `infra/` or `amplify/`), Bedrock integration, `scripts/` (seed data), demo script, deploys, budget alert, teardown |

These match quick-spec's default streams: Member 1 = @A (FE), Member 2 = @B (BE), Member 3 = @C (INFRA/QA).

How ownership changes by option:

- **Option B:** Member 3 owns `amplify/backend.ts`, auth and storage. Member 2 owns `amplify/data/` and `amplify/functions/`.
- **Option C:** Member 3 owns `Dockerfile` and `infra/`. Member 2 owns `app/src/`.

Ownership rules to write into `structure.md`:

- Each folder has one owner, which avoids merge conflicts. Changes to shared files (`tech.md`, the IaC template, the API client) are announced in the team chat first.
- A review is a five-minute second look, not a gate. Do not block the demo branch on it.
- The person who owns the IaC also owns the budget alert and the teardown command.
